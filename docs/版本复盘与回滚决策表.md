## 二、build_lists.py —— 413 行差异（唯一破坏源）

### 2.1 破坏点 A：v10.28.17 给 followable 加 `and _nf`（低频名单归零的真凶）

```python
# ── 昨日 v10.28.15 / v10.28.16（正常）────────────────────
# v10.21：followable 不再依赖 recent_circ_15d（改为生成时过滤），
#         避免已分配任务在清重生成时消失
followable = bool(is_lf) and (len(excluded) == 0)


# ── 今日 v10.28.17（致命）──────────────────────────────
_nf = shouldFollowUp(_build_op_history(aid))
followable = bool(is_lf) and (len(excluded) == 0) and _nf
#                                                   ^^^^^^ 新增第三个条件
```

**为什么会让名单归零** —— 追到 `_build_op_history()` 的输入构造：

```python
def _build_op_history(aid):
    orders = aid_orders.get(aid, [])
    for o in orders:
        sn = o['battery_device_sn']          # 从 cb_exchange_order 取 SN
        is_back = bool(sec) and (...)
        if is_back and (not sn or battery_circ.get(sn, {}).get('circ') == 0):
            sn_for_rule = '暂无电池'          # ← 致命点
```

而 `should_follow_up.py` 的规则是：

> 最后一条操作 == 「柜内归还电池」**且** 电池SN == 「暂无电池」 → **无需回访（返回 False）**

**本库实情**：流通表 `cb_battery_circulate_log` 无记录、订单表 `battery_device_sn` 取不到
（对应你日志里的 `[WARN] 电池定位跳过：records 里没有任何 battery_sn`）。

于是 `not sn` **恒为真** → 每条归还记录都被打上「暂无电池」→ `shouldFollowUp` 对
**所有低频候选** 返回 `False` → `_nf=False` → `followable=False`。

**这就是「低频用户: 0 ｜ 因流通异常剔除 6586」的成因 —— 6586 个是被 `_nf` 误杀的。**

### 2.2 破坏点 B：v10.28.18 字段自愈改造漏改一处（KeyError 崩溃）

改造本身有价值（线上 `cb_battery` 的 SN 列实际叫 `device_sn`，旧代码沿用 `battery_device_sn`
导致电池定位全空）。v10.28.18 加了运行期 `SHOW COLUMNS` 探测：

```python
def table_columns(cur, table):
    cur.execute("SHOW COLUMNS FROM %s" % table)

_R_AGR = pick_col(cur, 'cb_reception_log', 'agreement_id', 'exchange_agreement_id', 'agr_id')
```

**但 SELECT 改用别名后，取值处漏改**（你截图里的报错）：

```python
cur.execute(f"""SELECT `{_R_SLV}` AS _s, `{_R_TYP}` AS _t, COUNT(*) c
```
