📌 一、项目是什么

一套运行在用户自己电脑（Windows）上的本地部署低频用户回访系统。每天连阿里云 ADB 数据库抽数，自动判断哪些已签约换电的用户"协议生效但近期几乎不换电"（即低频用户），并把欠租催收对象一并整理，最终生成：

  • HTML 回访看板（浏览器打开，支持筛选/贴标签/短信结果列）
  • 低频用户名单、欠租催收回访名单（Excel + 看板 Tab）
  • 回访排班 / 回访调度（接待人分配、+N 天再次回访）
⚠️ 关键性质：数据不出本地、依赖内网/公网 MySQL，并非能在沙箱运行的在线应用。因此开发侧只能在沙箱改代码+打包，真实数据必须由用户在本机运行 .bat 生成。

核心数据流

build_lists.py（连库抽数）→ merge_sms_excel.py（并入短信）→ gen_dashboard.py（生成看板）→ export_special_lists.py（空号/停机）→ assign.py（自动分配接待）→ serve.py（0.0.0.0:8173 提供访问）

输出文件全部在 out/：records.json / assignments.json / staff.json / followup_dashboard.html / 回访名单.xlsx 等

8 月 12 号口径（当前生效）

协议生效天数累计归还电池次数 <档位
≤15 天不判定（新用户保护）—
>15 且 ≤30 天1 次L1
>30 且 ≤45 天2 次L2
>45 且 ≤60 天3 次L3
>60 天4 次L4
  • "归还电池次数" = cb_exchange_order 中 back_battery_time > 0 的订单数（只算归还）。
  • "生效天数" = NOW() − 协议生效时间。
  • 活跃母集 SQL：status IN ('working','owe_rent','unsubscribing') AND is_del=0，不按产品、不按协议类型过滤（个人+企业、全部产品都包含）。

阈值已配置化（重要，接手后勿改回硬编码）

自 v10.11 起，低频阈值由 db_conf.json 的 lowfreq_thresholds 控制，代码用 .get(..., 默认值) 兜底，改配置即可调口径，无需重打包。当前文件已切回 8月12号 数值：

"lowfreq_thresholds": {
  "protected_days": 15,
  "L1_max_days": 30, "L1_min_count": 1,
  "L2_max_days": 45, "L2_min_count": 2,
  "L3_max_days": 60, "L3_min_count": 3,
  "L4_min_count": 4
}
⚠️ 注意：db_conf.json 在 self_update 的 PRESERVE（保留） 列表里，自动更新不会覆盖它，因此用户本机改的阈值在更新后仍在。

「三千多 vs 一千多」问题结论

低频数从三千多掉到一千多，根因不是统计逻辑收紧，而是活跃母集（active_total）变小（数据库中大量协议 status 变成 finished/expired 或 is_del 被置 1）。放宽阈值只能在同一母集内多捞人，无法凭空回到三千多；要真正回到三千多需核对数据库母集是否被批量改动。

系统支持"在看板顶部填直链 → 点更新"的自更新体验，这是经过多轮修复后才跑通的，接手人务必保留：

  • 直链（zip 下载）：https://ae71ffa2092522eec.sh7.agentos-app.net/lowfreq_local_latest.zip
  • 发布方式：用 serve_publish.py（含 /lowfreq_local_latest.zip 动态打包路由）作为入口走「发布为应用」skill，重复发布会复用同一 token、覆盖旧 zip。
  • update_url.txt 已预填该直链，用户看板更新框默认预填。
  • self_update（auto_update.py）解压要求包内顶层必须是 lowfreq_local/ 目录；且必须保留 out/、uploads_sms/、db_conf.json、staff.json、update_url.txt（PRESERVE 列表）不覆盖。
⚠️ 历史坑：曾因发布方式从"静态 zip"改成"在线应用"导致 .zip 路径失效（HTTP 501），后补了 serve_publish 的 zip 路由才救回。发布前务必用 curl 实测直链返回 application/zip 且能解压出 lowfreq_local/。

🔒 七、沙箱环境限制（接手人必读）

沙箱 连不上用户的真实业务 MySQL（out/records.json 里是占位假数据、out/build_lists_error.log 是连库失败记录）。因此：
  • 开发侧只能在沙箱改代码 + 编译校验 + 发布 zip，无法在这里抽出真实名单。
  • 真实数据必须由用户在本机运行 fix_and_sync.bat 连内网库生成。
  • 验证逻辑可用"假数据单元复算"（如 13 个边界用例）确认口径正确，但不能替代真实库复算。
  • 沙箱测试起服务需先释放 8173 端口（fuser -k 8173/tcp），且 serve 日志要用 -u 无缓冲才能在发布脚本里被探测到。
