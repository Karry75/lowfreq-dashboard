低频用户口径对照与"三千多 → 一千多"差异溯源

本地部署版 lowfreq_local · 基于 build_lists.py 当前代码与对话记录推断 · 2026-08-18
一句话结论：现在"全部低频"还是一千多，不是统计逻辑把你算少了，而是活跃母集（active_total）比"三千多"那会儿小了一大截。而且反直觉的是——你记忆里"三千多"那版的口径其实比现在更严格（有"≤15 天新用户保护"），在同样的母集上它只会算得更少，绝不会更多。三千多是"更大母集 × 当时口径"的产物。

一、当前统计逻辑（build_lists.py 现状，已取消新用户保护）

看板"低频用户"按钮的计数 = records.json 里 lf=1 的行数，即后端判定结果，没有任何隐藏筛选压低数字。

活跃母集定义（v10.6 起逐字一致未改）：

SELECT ... FROM cb_exchange_agreement a
WHERE a.status IN ('working','owe_rent','unsubscribing') AND a.is_del = 0

低频判定（按协议生效后天数 use_days 与累计归还次数 total 分档）：

is_lf = False
if use_days is not None:            # 全部活跃协议参与，含新激活 ≤15 天
    if use_days <= 30:  is_lf = total < 1   # L1·≤30天档(<1次)
    elif use_days <= 45: is_lf = total < 2   # L2·30~45天档(<2次)
    elif use_days <= 60: is_lf = total < 3   # L3·45~60天档(<3次)
    else:                is_lf = total < 4   # L4·>60天档(<4次)

二、"三千多"是怎么来的（旧口径推断）

对话与代码注释表明，"三千多"那个时期的判定多了一条新用户保护：

# 旧逻辑（取消保护前）
if use_days is not None and use_days > 15:   # 仅 >15 天才参与判定
    if use_days <= 30:  is_lf = total < 1   # L1
    elif use_days <= 45: is_lf = total < 2  # L2
    elif use_days <= 60: is_lf = total < 3  # L3
    else:                is_lf = total < 4   # L4
# use_days <= 15 的新用户：直接不算低频

也就是说，旧版排除了所有刚激活 15 天内的新用户，判定更严格。它之所以能算出三千多，靠的是当时更大的活跃母集——大量协议仍处在 working / owe_rent / unsubscribing 且 is_del=0 的状态。

三、为什么取消保护 + 全部低频后还是一千多

这里有两个相反方向的因素在拉扯：

因素方向对低频数的影响
阈值效应 取消 ≤15 天保护，口径变宽 同母集 → 低频 ↑ 让数字变大（新口径比旧口径更宽松）
母集效应 活跃协议母集缩小（status / is_del 变化） 母集 ↓ → 低频 ↓ 让数字变小，且是主导因素
核心反直觉点："三千多"那版口径更严格（有 15 天保护）。所以即便在同一个母集上，旧口径算出的低频也只会 ≤ 现在（取消保护后）的结果。之前数字高，纯粹是因为当时母集比现在大得多。

四、按"之前的统计逻辑"在现在的母集上会是多少

把"旧口径（带 15 天保护）"套到当前这份 records.json 上复算，结果只会等于或略小于现在的一千多——绝不可能回到三千多。要回到三千多，必须先让 active_total 回到当年的量级，而不是调阈值。

已附对照脚本 lowfreq_local/analyze_lf.py，在你本地（能连库、已生成真实 records.json 的环境）运行：

cd lowfreq_local
python analyze_lf.py

它会输出：active_total、当前口径低频数、旧口径低频数、两者差（应为 ≤0，印证新口径更宽）、以及新口径各档位分布。用这一个数字就能看穿"是母集缩了还是逻辑变了"。

五、如何验证"母集确实缩小了"

① 看板自带的 diagnostic 面板：打开看板 → 诊断区查看 active_total 与当年截图对比。

② 直接查数据库 status 分布（若比当年少一大截，即母集缩小主因）：

SELECT status, COUNT(*) c
FROM cb_exchange_agreement
WHERE is_del = 0
GROUP BY status;

若大量协议 status 变成了 finished / expired / closed / refunded 等非活跃值，或 is_del 被批量置 1，那就是母集缩小的来源——这发生在抽数 SQL 之前，任何前端/阈值改动都无法让它们重新进入统计。

六、下一步建议

  • 先定位母集变化：跑上面 SQL，确认是真实退订潮，还是 status 被批量误改/口径漂移。前者是业务事实，数字就该低；后者需从源库纠正。
  • 若确需放宽活跃定义：可在 db_conf.json 配置 extra_statuses（如把 finished 等纳入），系统已有可配置位，不要改 SQL 硬编码。
  • 阈值保持现状即可：当前已是最宽松（无 15 天保护、全产品参与），再放宽也不会让母集回升，反而会把真实活跃用户误判为低频。
