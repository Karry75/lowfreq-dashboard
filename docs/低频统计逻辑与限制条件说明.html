低频用户统计思维 · 逻辑 · 限制条件 · 筛选机制

一句话结论：「低频」=「签了换电协议、但近期几乎不换电」的用户，目的是筛出需要电话/短信唤醒的人。 整套统计没有按产品、协议类型砍数据——深圳4824 看到的400多，是它自己在活跃母集里的真实切片， 不是被算少了；而三千多/1717 是所有产品加总的全量，和单一产品不是同一量级。

一、统计思维（为什么这么算）

核心目标只有一条：找出"协议在生效、但电池几乎不流动"的用户。换电次数越少，说明用户越不活跃、越可能流失或沉睡。

  • 用「归还电池次数」衡量活跃度——借了又还才有换电行为；长期不还 / 不借，就是静止。
  • 用「协议生效天数」分档——刚激活的用户换电少是正常的（新用户保护），老用户换电少才异常。
  • 不满足"任一档"的，就是正常活跃用户，不进回访名单。

二、统计逻辑（判定公式）

低频 = 在「活跃协议母集」中，按"协议生效天数"分档，累计换电次数低于阈值的协议 判定维度：cb_exchange_order.back_battery_time > 0 的订单数（DISTINCT 订单ID），即「归还电池次数」 数据截止：cb_exchange_order 中最新一条 back_battery_time（覆盖到 2026 年）
协议生效天数（use_days）判定：累计换电次数 <档位含义
≤ 15 天— （不判定）保护新激活用户，换电少属正常，不计入低频
15 ~ 30 天3 次L1最严重：近半月几乎没换电
30 ~ 45 天4 次L2较严重
45 ~ 60 天5 次L3中等
> 60 天9 次L4最轻：老用户长期低频

阈值来自 db_conf.json 的 lowfreq_thresholds，可本地自行调宽/调严，无需重新打包。

三、限制条件（什么会被排除 / 缩窄）

这是"三千多 → 一千多"的真正原因所在，按影响从大到小：

限制点具体规则影响
母集活跃协议定义status IN ('working','owe_rent','unsubscribing') AND is_del=0主导因素。退订/到期/被误删的协议都不算，母集越小低频越少。
新用户保护生效 ≤15 天不参与判定不把刚激活的用户误判为低频。
换电口径只算"归还电池"back_battery_time>0，不算"取电池"仅有效归还事件计入；仅借不还很久没还的，次数低→偏低频。
时间窗口以最新归还时间为 NOW 截止；各档只统计窗口内次数历史老订单不影响当前分档。
阈值L4<9 等（v10.11 放宽版）调大→低频变多，调小→变少。
关键提醒：以上限制全部作用在「全量母集」上，对所有产品一视同仁。没有任何一条是"只针对深圳4824"或"按产品类型豁免"。所以深圳4824的低频少，不是限制条件在针对它。

四、筛选机制（前端怎么"看"）

看板顶部的筛选（省市区街道 / 电池产品 / 协议类型 / 协议状态 / 是否低频 / 档位 / 协议ID / 关键词）都是视图筛选——它们只是从全量 records.json 里挑出子集给你看，不会重新计算或砍掉数据。

  • 协议类型：默认"全部（个人+企业）"，不限制。之前默认"个人"的坑已修复。
  • 电池产品：下拉选某产品后，KPI 的「低频用户」= 该产品 且 is_lf=1 的数量。选"深圳4824"看到400多，就是它真实的低频切片。
  • 诊断面板：展示活跃协议总数、各产品分布、全表状态分布，用来核对母集有没有异常缩小。
所以：你看到的每个数字，底层都是 records.json 里真实算出来的，前端没有二次运算、没有隐藏过滤。

五、为什么"深圳4824低频才四百多"——认知澄清

最大的认知陷阱：把「全量低频」和「单一产品低频」当成同一量级。
  • 三千多 / 1717 = 所有电池产品加总的全量低频（深圳4824 + 杭州4824 + 阳朔4824 + 各4814 + 其它产品）。
  • 深圳4824 = 其中一个产品的低频切片。6个优选产品每个400~600，加起来就已接近三千多。

其次，深圳4824 是高频换电产品——用户天天换电，累计换电次数天然高，低频比例本就偏低。如果它低频都上千，那反而不正常（说明用户都不用了）。

真正的判断标准只有一个：深圳4824在活跃母集里到底有多少协议？

  • 若深圳4824活跃协议只有 ~700~900 个，低频400多（占比50%+）——完全正常，甚至偏高。
  • 若深圳4824活跃协议有数千却只低频400多——那要查"低频用户平均换电次数"，如果平均换电很高，说明产品本身就高频，低频少是正常现象。
还有一处要核对：下拉里"深圳4824"对应的 product 名称必须和数据库 cb_battery_product.name 完全一致（精确匹配）。若库里实际叫"深圳4824电池"或"4824型"，你选"深圳4824"会匹配不到，数字就会偏小。请在看板下拉里确认实际选项文字。

六、怎么自己核对真相（30秒）

已为你准备好脚本 lowfreq_local/analyze_products.py，直接读你本地刚同步的 out/records.json，按产品统计：

cd lowfreq_local python3 analyze_products.py

输出每个产品的：活跃协议数 / 低频用户 / L1~L4 各档 / 低频占比 / 平均累计换电，并单独高亮含"4824/4814"的产品。一看就知道深圳4824的400多是怎么来的。
