低频用户统计口径与数量骤降排查说明

适用版本：v10.8.5（与 v10.6 ~ v10.8.4 统计逻辑完全一致，本版未改动任何统计代码）
一句话结论：低频用户数量从 3000+ 降到 1000+，不是统计算错、也不是数据不准，而是统计的母集（活跃协议）变小了——这是数据库侧（协议 status 被改 / 被打 is_del=1）引起的输入变化。低频是活跃协议的子集，母集缩了，子集必然缩。

一、统计思路（5 步流水线）

① 定数据截止 NOW→ ② 圈活跃协议母集→ ③ 算累计换电次数 total→ ④ 算生效天数 use_days→ ⑤ 低频判定 + 分级

① 数据截止时间 NOW

取值
NOW = MAX(back_battery_time)，取自 cb_exchange_order（即"最近一次成功归还/换电"的时间）
作用
所有"天数 / 时间窗口"都相对 NOW 计算。只影响 L1~L4 的分档，不影响低频"是否命中"（因为各档阈值 1/2/3/4 是固定值）

② 圈定"活跃协议"母集（所有名单的源头）

SELECT ... FROM cb_exchange_agreement a
  LEFT JOIN cb_battery_product p ...
  LEFT JOIN cb_site s ...
WHERE a.status IN ('working','owe_rent','unsubscribing') AND a.is_del=0
含义
这就是"全部活跃协议"数字，也是"欠租催收""低频用户"的共同母集
版本一致性
v10.6 → v10.8.5 该 SQL 完全相同，未改

③ 累计换电次数 total（每条活跃协议）

来源
cb_exchange_order WHERE back_battery_time>0 AND is_del=0，按 exchange_agreement_id 聚合 COUNT(DISTINCT id) AS total
含义
"该协议生效以来，成功换电（归还）了多少次"

④ 协议生效天数 use_days

计算
use_days = (NOW − activation_time) ÷ 1天
保护
生效 ≤15 天 的协议直接不进入低频判定（新用户保护）

⑤ 低频判定与分级（仅 use_days>15 才判定）

生效天数区间判定条件 (total)档位
15 ~ 30 天total < 1L1 · 15~30天档
30 ~ 45 天total < 2L2 · 30~45天档
45 ~ 60 天total < 3L3 · 45~60天档
> 60 天total < 4L4 · >60天档
命中任一档 → is_lf = True → 计入"低频用户"。维度提示：看板/Excel 里"低频用户数"有两个口径——份数（协议数 len(lf_list)）和去重用户数（len(set(user_id))），别混用。

二、为什么数字会从 3000+ 掉到 1000+（核心排查）

低频数量只由两个输入决定：活跃协议母集大小 + 各协议的换电次数 total。代码没动，所以下降只能来自这两个输入的变化：

可能原因对低频数量的影响是否符合"下降"
活跃协议母集缩小
（大量协议 status 被改 / 被打 is_del=1）		 母集从几千条→几百条，低频作为其子集同比例缩小 ✓ 正是下降方向
换电记录变少
（back_battery_time 被清 / is_del 被置 1，total 变小）		 total 越小越容易命中低频，低频数量会上升而非下降 ✗ 方向相反

结论：出现"下降"，恰恰说明是母集在缩，而不是换电记录少了。这与昨天排查的"关深圳4824 活跃协议从三千多→一百多"是同一根因——你两次看到的是不同维度（一个是全部低频，一个是深圳4824 这一个产品的活跃数），根子都在于数据库里这批协议的状态 / 删除标记变了。

三、怎么坐实"是数据库侧变化"（自助验证）

看板上
升级 v10.8.5 后，打开「数据说明」里的 diagnostic 面板，重点看：
· active_total（当前活跃协议总数）
· all_status_count（全表 is_del=0 各 status 分布）
· active_type_count / active_product_count
对比法
把现在的 active_total 与你记忆中 v10.6 时期的同名数字对比：
· 若全表 working/owe_rent/unsubscribing 本身就少了几千条 → 协议状态被改；
· 若全表总数正常但活跃数变少 → 被打了 is_del=1。
文件佐证
每次抽数 build_lists.py 都会写出 out/diagnostic.json 并在 records.json 内嵌 diagnostic，可直接拿给 DBA 核对。

四、关于"系统更新里填直链的框不见了"

已核验：v10.8.5 的发布包、生成的 followup_dashboard.html、以及后端 /api/self_update 接口三者都完好。看板最顶部的「系统更新」横幅里，一直有"粘贴更新包直链"输入框 + 「检查并更新」按钮。看不到通常是以下原因：
